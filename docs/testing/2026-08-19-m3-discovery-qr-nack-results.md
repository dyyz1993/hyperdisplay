# M3 实测记录：局域网发现 + 扫码 + 关键帧 NACK（2026-08-19）

环境：macOS 26.2 · 华为 DBY2-W00 平板（已解锁，WiFi **2.4GHz**：SSID 360WiFi-193784，
链路速率 78Mbps Tx / 104Mbps Rx）

## 1. 局域网发现（Bonjour / mDNS）——真机闭环 ✅

- host 侧 `dnssd DNSServiceRegister` 广播 `_hyperdisplay._udp`（不占数据 socket），
  Mac 本机 `dns-sd -B` 可见 `Hyperdisplay (MacBook Pro)`；
- 平板「局域网发现」→ NsdManager 解析出 **192.168.0.9:5277** → 点击列表项 → 连接建立
  （host 日志 HELLO，浮层 `HEVC 2800x1840 · 链路 OK`）；
- 华为 NsdManager 首次注册偶发失败 → 已加自动重试；「停止回调勿覆盖错误信息」修复。

## 2. 扫码连接

- host 菜单栏「显示连接二维码…」→ CIQRCodeGenerator 生成 `hyperdisplay://<ip>:<port>` 面板
  （列全部网卡地址；USB 网卡时扫对应地址即走 USB 通道）；
- 客户端 zxing（与 hypercast 同款依赖）扫码 → 解析 `hyperdisplay://` 或裸 `ip:port` → 连接。
- 相机扫码需人工持机对准 Mac 屏，未自动化验证；解析与连接路径与手动输入共用，已由
  局域网发现路径等效验证。

## 3. 大关键帧丢片治理（2.4GHz 根因链）

现象：2800×1840 档关键帧 600–800KB（554–733 分片），平板实测**单帧丢片率 13–21%**
（NACK resent=94/733、157/733）→ 大帧几乎无法完整 → 画面恢复极慢。

修复链（全部实测有效）：

| 措施 | 效果 |
|---|---|
| host 发送背压重试（EWOULDBLOCK 睡 2ms 重试，替代直接 break 丢剩余片） | 消除自残式丢片 |
| 分片节流（64 片 / 1.5ms） | 降低瞬时突发 |
| 自动码率 5→3.5 Mbps/MP，显式 12Mbps | 关键帧 800KB→~600KB（12Mbps 档首帧 106KB） |
| **关键帧分片 NACK**（host 缓存近 8 个关键帧分片；客户端 stall/abandon 上报缺失片，255 片/包分批） | 补齐丢失分片（resent=6~157 实测生效） |
| 等关键帧且无分片到达时周期性请求 IDR（idle-wait） | 首帧全丢场景恢复 |

**最终实测**：平板 2.4GHz 下 2800×1840 **动态拖动 40fps**；静态桌面正确显示（内容驱动
0fps 是诚实值，画面清晰完整，视觉验证通过）。

## 4. 结论与建议

- 2.4GHz（78Mbps 链路）是当前环境的根本瓶颈；**平板切到 5GHz 路由器频段预期质变**
  （分片丢失率数量级下降，NACK 几乎不需要）。
- USB 网络共享不经过 WiFi，天然免疫此问题，推荐对延迟/稳定性敏感时使用。
- 后续可选优化：按实测丢片率自适应码率/分辨率；关键帧强制低 QP 上限；FEC。
